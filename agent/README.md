# Agent 开发学习路线（18 周）

> 目标：掌握通用的 Agent 开发原理与工程方法，不绑定具体业务项目。
> 形式：Markdown 学习路线与笔记；实践使用小脚本或 CLI，不要求开发页面。
> 起点：会编程，Python 和 LLM 基础需要补齐。
> 投入：每周 10～15 小时，18 周约 180～270 小时。
> 修订日期：2026-10-16。

## 1. 学习目标

学完后，应能独立解释、实现并验证以下能力：

1. 调用模型接口，处理多轮消息、流式输出和结构化结果。
2. 定义工具，校验参数，执行工具并正确回传结果。
3. 手写 Agent 循环，理解任务决策、执行反馈和停止条件。
4. 管理上下文、短期状态与长期记忆。
5. 理解 RAG 的作用，并判断错误发生在检索还是生成阶段。
6. 根据任务选择固定 Workflow、动态 Agent 或两者结合。
7. 使用状态机、检查点和人工确认管理较长任务。
8. 通过 MCP 复用工具能力，理解协议与应用逻辑的边界。
9. 用评估、日志、预算和权限控制提升可靠性。
10. 理解多智能体的适用条件，能与单 Agent 做对照。

每阶段用一个小实验验证机制。最后可以自选综合练习，但不预设为某种助手，也不要求所有实验合成一个产品。

## 2. 主线与范围

**Python 必要基础 → LLM 应用基础 → 工具调用 → Agent 循环 → 上下文与记忆 → RAG → Workflow 与状态管理 → MCP → 评估与可靠性 → 多智能体 → 综合复盘。**

评估从工具调用阶段就开始积累，不等学完全部内容才测试。

### 为什么这样安排

- 先学模型输入输出，才能看懂工具调用的消息流。
- 先手写循环，才能理解框架替你管理了什么。
- 先理解上下文与记忆，再区分资料检索和长期事实保存。
- 先掌握单 Agent 和状态管理，再研究跨客户端工具协议与协作。
- 用结果决定是否增加复杂度，而不是为了学框架不断重写。

### 暂不作为必修的内容

模型预训练、微调、强化学习、GPU 集群、复杂数据库运维、Web 页面和公网部署。它们不是理解 Agent 的前提。

## 3. 技术选择

| 部分 | 建议选择 | 学习目的 |
|---|---|---|
| 语言 | Python 3.12 | 固定稳定环境，集中精力学习机制 |
| 环境与依赖 | uv | 学会项目隔离、依赖声明和锁定 |
| 模型调用 | `openai` Python SDK + 国内兼容接口 | 理解消息协议与调用过程 |
| 初始服务商 | DeepSeek；基础跑通后再选 Qwen 或 GLM 对比 | 先减少变量，再学兼容性差异 |
| 参数与输出校验 | Pydantic | 区分格式、类型和业务约束 |
| 测试与记录 | pytest、JSONL | 程序测试、执行轨迹与任务评估 |
| 数据持久化 | JSON；确有查询需求再用 SQLite | 管理状态与记忆 |
| 检索实验 | 关键词基线 + 一种 Embedding + Chroma | 理解检索链路，不同时研究多个向量库 |
| 编排框架 | LangGraph，手写循环之后再学 | 对比状态、检查点、人工介入 |
| 工具协议 | MCP 官方 Python SDK | 理解工具服务和客户端集成 |

使用兼容接口时，基础调用方式可以复用，但思考模式、结构化输出、流式工具调用等仍可能有差异。模型名、价格、参数和协议版本在实际使用时查官方文档，不把旧示例当成固定事实。

本路线只规定学习和实验内容，不要求现在安装依赖或创建所有目录。学习笔记与实验代码可以按阶段分别整理。

## 5. W1：Python 与工程基础

**要学什么**

- 列表、字典、函数、模块和文件读写。
- 类型注解、异常处理、日志和基础单元测试。
- JSON、环境变量、虚拟环境、依赖声明与锁文件。
- 了解 `async/await`；先把同步程序写清楚，再处理并发。

**实践**

写一个 JSON 数据处理脚本：读取测试订单，计算每笔金额和总额，输出汇总文件。输入使用自己编写的虚构数据，不接真实业务系统。

用 uv 管理练习环境，检查实际解释器版本，不依赖旧笔记里记录的本机配置。已有基础可直接用验收判断是否跳过部分语法学习。

**验收**

- 正常数据、空数据、文件缺失、字段错误都有明确行为。
- 能顺着 traceback 找到错误位置。
- 能解释工作目录、模块路径和依赖安装位置。
- 不看教程能增加一个统计字段。

**笔记重点**：解释器、环境、依赖、数据校验分别解决什么问题。

## 6. W2～W3：LLM 应用基础

### W2：一次调用与多轮对话

**要学什么**

- LLM 根据上下文生成输出，不等于数据库或规则引擎。
- 消息角色、消息列表、上下文窗口、输入和输出 token。
- 客户端如何保存多轮历史；模型接口不会自动替应用保存所有对话。
- Prompt 中的任务、约束、示例与输出格式。

**实践**：实现最小 CLI 聊天，支持连续对话、清空历史和退出；打印请求中的消息摘要、耗时和 token 用量。

密钥从环境变量读取。本地使用 `.env` 时显式加载，不能只创建文件就假设变量已进入进程。真实密钥排除出版本控制。

**验收**：能手动写出三轮对话的消息列表，并解释删掉历史后回答为什么变化。

### W3：流式、结构化输出与参数实验

**要学什么**

- 流式事件和完整响应的区别，如何拼接增量内容。
- 采样参数、输出限制及当前模型实际支持的配置。
- JSON 合法、Schema 合法、业务正确是三层要求。
- 思考模式可能影响输出、延迟和成本，不依赖模型提供完整思维链。

**实践**：给 CLI 增加流式输出；从一段虚构订单描述中提取商品、数量和地址，用 Pydantic 校验。对固定输入比较两种提示词的效果，每种重复少量运行。

**验收**：非法 JSON、缺字段、错误类型、业务值不合理能区分；流式用量未返回时标为未知；能说明实验结果和样本限制。

**笔记重点**：模型输出的不确定性，以及程序怎样约束它。

## 7. W4：工具调用机制

**要学什么**

- 工具名称、描述、JSON Schema 和参数校验。
- 模型返回工具请求，应用程序负责实际执行。
- 助手工具请求消息、`tool_call_id`、工具结果之间的对应关系。
- 结构化输出用于生成数据，工具调用用于请求执行能力；二者相关但不等同。

**实践**

实现 `get_current_time` 和 `convert_units` 两个工具。手写“请求模型 → 接收工具请求 → 校验并执行 → 回传结果 → 再请求模型”的完整过程。

先做非流式工具调用，看清消息后再研究流式参数如何拼接。一次响应可能包含多个工具请求，逐个正确处理。

故意模糊工具描述，观察是否选错工具；再改进描述做对照。

**从这一周建立评估集**：先有 5 条任务，覆盖正常调用、不需要工具、缺少信息、参数错误和工具失败。

**验收**：能指出工具在哪一行被执行，能完整解释两次模型请求分别收到了什么。

## 8. W5～W6：手写 Agent 核心循环

### W5：循环与任务完成

**要学什么**

- Agent：模型根据任务和执行反馈动态选择下一步。
- Workflow：程序预先规定步骤与分支；两者可以结合。
- 工具执行反馈、最终回答、失败与停止条件。
- ReAct 的思考、行动、观察思想；工程实现不要求公开或保存完整内部思维链。

**实践**

准备一份虚构商品目录，提供查询价格、查询库存、计算总价三个工具。完成“某预算内比较两种商品并推荐”的组合任务。

手写循环，不使用 Agent 框架。设置最大模型次数、工具次数、任务超时、输出限制。日志记录运行编号、动作、参数摘要、结果、状态、耗时和用量。

**验收**：约 10 条任务可重复运行；能还原多步轨迹；编造工具名被拒绝；用完步数后明确说明任务未完成。

### W6：错误反馈、权限与副作用

**要学什么**

- 哪些错误可以反馈给模型，哪些由程序重试或停止。
- 读操作与有副作用的写操作、确认、幂等和取消。
- 提示词约束不能替代程序权限控制。

**实践**：增加模拟订单草稿工具；模型生成草稿，用户明确确认后程序才提交到测试数据。记录操作编号，避免重复提交。

| 情况 | 处理方式 |
|---|---|
| 参数缺失或不合法 | 返回结构化错误，有限纠正或向用户澄清 |
| 只读请求短暂网络故障 | 程序有限重试，设置退避与超时 |
| 权限拒绝、预算耗尽 | 程序停止，不交给模型绕过 |
| 写入结果未知 | 先检查是否已经执行，不盲目重复 |

重复工具与参数是异常线索，不应一律中止；查询状态等任务可能需要重复调用，要结合结果变化和总上限。

**验收**：错误参数、取消、拒绝执行、确认执行、重复请求都有测试；能画出循环和数据流。

## 9. W7：上下文与记忆

**要学什么**

- 上下文是本次模型看到的输入，历史是应用保存的数据，两者不完全相同。
- 短期状态、对话摘要、长期记忆、外部知识库的区别。
- 滑动窗口、摘要压缩、按需加载，及其信息损失。
- 长期记忆的来源、更新、冲突、过期与删除。

**实践**

用一段人工构造的长对话比较完整历史、窗口裁剪、摘要三种方式；检查早期约束是否保留。保存几条虚构偏好到 JSON，再执行查询、更新和删除。

裁剪历史不能拆散工具请求与对应结果。摘要需保留任务目标、已确认事实、约束、执行状态和来源。

**验收**：展示摘要遗漏与事实冲突各一例；删除记忆后下一次请求不再注入；能解释“保存了数据”不等于“模型一定用到数据”。

## 10. W8～W9：RAG 与知识增强

### W8：检索基线与最小 RAG

**要学什么**：文本切分、元数据、Embedding、相似度、top-k、向量索引，以及检索和生成各自的职责。

**实践**：自备 10～20 篇公开的产品说明或虚构 FAQ，保留来源与使用范围。先做关键词检索，再为同一语料建立向量索引，最后加入基于检索结果的回答。

准备约 15 条问题，标注答案要点和证据片段，包含至少 3 条无答案问题。引用使用片段编号，由程序映射到实际来源，不能直接相信模型生成的链接。

**验收**：能单独检查检索结果；能给出可核对引用；无资料时说明不足。

### W9：检索优化与失败定位

**要学什么**：BM25、中文分词、混合检索、Rerank、索引更新和证据支持程度。

**实践**：一次改变一个变量，比较切分、top-k、混合检索或重排中的一项。有余力再做第二项，不要求把全部技术堆进去。

记录检索命中、回答质量、延迟和成本。对文档增删改进行索引更新验证；来源位置要对应正确内容版本。

**验收**：展示检索未召回、生成未使用证据两类失败；引用编号有效与引用支持结论分开检查；评估任务累计约 20 条。

**边界**：RAG 是知识增强方式，不是所有 Agent 的必备组件，也不是有向量库就自然拥有记忆。

## 11. W10～W11：Workflow、状态管理与框架

### W10：先把控制流写清楚

**要学什么**

- 链式执行、路由、并行、生成与评审循环。
- 动态决策与固定流程分别适合什么任务。
- 显式状态、节点输入输出、分支、错误状态和终止状态。

**实践**：以虚构售后申请为例，编写固定的“解析申请 → 查询规则 → 生成建议 → 检查结果”流程。再用 Agent 循环处理同一任务，对比正确率、调用次数和可解释性。

**验收**：能说明哪种方案更适合当前任务，而不是默认 Agent 越自主越好。评审循环有次数上限。

### W11：检查点、恢复与人工介入

理解状态保存、检查点、暂停、继续、重放以及副作用重复执行。再用 LangGraph 实现 W10 的一个小流程，对照自己写的版本。

**实践**：在模拟写操作之前暂停等待用户确认；保存状态，重启后恢复。已经完成的写操作不重复提交。

**验收**：保存和恢复过程有可复现记录；能区分“保存对话”“恢复执行状态”“重新从头运行”；能解释框架具体省去了什么工作。

不要求把前面全部实验迁移到框架。

## 12. W12～W13：MCP 与工具生态

### W12：协议与 Server

**要学什么**：Host、Client、Server 的职责，Tools、Resources、Prompts 的区别，本地 stdio 与远程 Streamable HTTP 的场景。

**实践**：用官方 Python SDK 把已有单位换算、商品查询工具封装为本地 MCP Server，复用原业务函数。先实现 Tools，不要求一次实现全部协议能力。

检查 SDK、客户端和协议版本兼容性，不根据旧教程手写协议。stdio 的普通日志写入 stderr，避免污染协议输出。

**验收**：用 Inspector 或支持的客户端列出工具并成功调用；能看懂输入输出与错误结果。

### W13：客户端接入与能力边界

用一个支持 MCP 的实际客户端调用 Server；如果有余力，再写最小客户端体验发现工具、调用工具和处理结果。

对比本地函数调用与 MCP：协议解决发现、描述和调用等互操作问题，业务函数仍需负责正确性与权限。

**验收**：保存版本、配置、启动方式和成功轨迹；能解释 MCP 与 Tool Calling 的关系；理解“通过 MCP 接入”不代表工具安全或回答正确。

初版以只读工具为主，有副作用的工具必须有明确授权与重复执行保护。远程认证和公网部署不作为本阶段必修。

## 13. W14～W15：评估、可观测性与可靠性

### W14：把已有实验整理成评估套件

从前期案例整理至少 30 条任务，按工具调用、组合任务、无答案、错误处理、权限、引用等分类。

每条包含输入、结果要求、必要工具或禁止行为、评分规则、数据版本。允许合理的不同执行路径，不把唯一工具序列当正确答案。

约 20 条用于开发，约 10 条保留为阶段验收；固定模型、Prompt、工具版本、数据和运行参数。

| 指标 | 看什么 |
|---|---|
| 任务成功率 | 最终目标是否完成，必要副作用是否真的发生 |
| 工具使用 | 选得对不对、参数是否合法、有没有越权 |
| 检索与引用 | 是否召回证据，引用是否支持结论 |
| 效率 | 调用次数、耗时、token、估算费用 |
| 失败类型 | 参数、检索、推理、权限、网络、状态恢复分别占多少 |

程序性检查用规则，语义判断先人工；模型裁判需要人工抽查。对少量代表性任务重复运行观察波动，不能用一次小样本成绩承诺通用成功率。

**验收**：输出方法、样本数、结果、失败分析，不为了好看删掉困难样本。

### W15：故障实验与性能改进

**实践**：制造超时、限流、工具报错、用户取消、进程退出、外部内容提示词注入等至少 6 类场景，明确预期与实际行为。

区分重试和恢复。请求超时不代表服务端没处理或计费；写操作必须检查状态再决定是否重试。

记录任务与步骤轨迹，区分用户可见摘要和敏感原文。先用 JSONL，确有分析困难时再选 Langfuse 等追踪工具。

从日志选择一个实际瓶颈优化，例如减少无效调用、裁剪上下文或并行独立只读工具。不能并行的依赖和副作用仍保持顺序。

**验收**：故障不会造成静默失败或重复提交；一项优化有前后对照；费用上限、调用上限和超时能生效。

## 14. W16：多智能体

**要学什么**

- 主从分工、路由、并行工作者、生成与评审模式。
- 子任务输入输出契约、上下文隔离、结果汇总和失败传播。
- 多 Agent 不等于给几个角色名字，多模型调用也不必然是多智能体。
- 固定“生成—评审”可以是 Workflow，不必称为自主多 Agent。

**实践**：提供几份固定公开资料，让单 Agent 先完成比较报告；再用两个工作者分别处理独立资料，由主 Agent 汇总。只读、固定材料，先排除搜索和写入带来的变量。

比较任务质量、遗漏、延迟、调用次数、费用；检查子 Agent 的结论能否追溯到原资料。

**验收**：能说明什么时候并行或上下文隔离有收益，什么时候单 Agent 更简单；不要求多智能体一定胜出。

## 15. W17～W18：自选综合练习与复盘

### W17：选择一个范围受控的任务

可选方向：公开资料研究、虚构客服流程、结构化数据分析、受限目录文件整理。也可以提出其他任务，不限定为某个业务助手。

优先复用已验证的小实验，整合核心能力，不在最后两周从零搭大系统。只选任务需要的工具、检索、记忆或框架，不要求全部用上。

写清任务目标、成功标准、权限范围、停止条件和评估案例。冻结功能后修复主要失败。

**验收**：选型有理由，正常和失败路径都能演示，未完成的限制明确列出。

### W18：复现与原理总结

整理运行说明、依赖、脱敏配置、示例数据、评估方法、结果和失败案例。在新环境按说明复现，完成三个代表性任务；无需页面和公网部署。

技术复盘回答：

1. 模型、工具、Agent 循环和执行环境各负责什么？
2. Workflow 和 Agent 如何选择？
3. 上下文、状态、记忆、RAG 分别解决什么问题？
4. 工具参数、权限、副作用和重试怎样受程序控制？
5. MCP 与框架分别处在哪一层？
6. 多智能体带来的收益是否值得额外复杂度？
7. 成功率、耗时、成本怎么测，有什么样本限制？
8. 还有哪些失败不能可靠处理？

**最终成果**：阶段学习笔记、可运行的小实验、自选综合练习、评估报告和复盘。学习笔记所在仓库不决定练习的业务主题。

## 16. 学习方法与笔记要求

每周只设一个核心目标；2 小时读文档，6～9 小时实验，1～2 小时验证，1～2 小时整理笔记。

每篇学习笔记回答五件事：

1. 这个概念解决什么问题？
2. 输入输出和关键数据结构是什么？
3. 最小实验怎么验证？
4. 遇到了什么失败，原因是什么？
5. 什么情况下不需要这项技术？

不以抄了多少代码、读了多少教程作为完成标准。遇到问题先缩小实验；理解机制后可以借助 AI 辅助编码，但要能解释关键控制流和边界。

程序测试尽量不依赖模型，任务评估才调用真实模型；小样本调试通过后再完整跑批。

费用设个人月度上限，先小额使用，按平台实际账单核对。应用估算保留模型、币种和价格日期，流式用量未知时不要计为 0。达到预算后用假模型和已有轨迹继续学习，不强行跑付费评估。
