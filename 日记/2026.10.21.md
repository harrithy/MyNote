## 🔥 核心难点、关键代码与攻坚复盘

### 1. 64 位分布式消息 ID 在 JS 中的精度丢失与时序震荡

- **涉及文件**：`D:\yin\gddst-coss-frontend\src\store\im\messageOrder.ts`、`D:\yin\gddst-coss-mobile\common\im\messageOrder.js`
- **难点所在**：后端推送的雪花算法（Snowflake）消息 ID 为 64 位大整数，直接被 JS 转为 Number 时会丢失尾部精度，导致后发消息排到前面，产生列表跳动与乱序。
- **关键代码**：

```typescript
/** 将消息的正整数正式 ID 转成十进制字符串；0、缺失值和非法值视为本地消息。 */
const getMessageId = (message: Pick<ChatMessage, "id">): string => {
  const id = String(message.id ?? "").replace(/^0+/, "");
  return /^[1-9]\d*$/.test(id) ? id : "";
};

/** 比较两条消息：正式 ID 升序，无正式 ID 的消息置后；字符串比较避免大整数精度丢失。 */
export const compareMessageOrder = (
  left: Pick<ChatMessage, "id">,
  right: Pick<ChatMessage, "id">,
): number => {
  const leftId = getMessageId(left);
  const rightId = getMessageId(right);
  if (!leftId || !rightId) {
    return leftId ? -1 : rightId ? 1 : 0;
  }
  return (
    leftId.length - rightId.length ||
    (leftId < rightId ? -1 : leftId > rightId ? 1 : 0)
  );
};
```

- **攻坚方案**：自实现“字符串长度比较 + 字符字典序”的高精度排序器；未拿到服务端的本地临时消息（未分配 ID）统一置后，并保留原始索引作为稳定性保底。

### 2. 消息高频刷屏下的持久化 IO 瓶颈与异步倒挂

- **涉及文件**：`D:\yin\gddst-coss-frontend\src\store\im\chatStore.ts`
- **难点所在**：群聊短时间内涌入大量消息时，每次变更若全量落盘会引发卡顿甚至锁死；异步持久化还可能出现先发批次后完成、旧数据覆盖新数据的时序倒挂。
- **关键代码**：

```typescript
/** 每个 Store 独立串行保存，避免旧写入覆盖新数据或错误确认新修改。 */
interface ChatPersistenceState {
  userId: number | string;
  generation: number;
  pending: Map<string, PendingChatWrite>;
  queue: Promise<void>;
}

const chatPersistence = new WeakMap<object, ChatPersistenceState>();

/** 获取指定 Store、用户的保存队列；切换账号时取消旧批次，但保留串行执行顺序。 */
const getChatPersistence = (
  store: object,
  userId: number | string,
): ChatPersistenceState => {
  let state = chatPersistence.get(store);
  if (!state) {
    state = {
      userId,
      generation: 0,
      pending: new Map(),
      queue: Promise.resolve(),
    };
    chatPersistence.set(store, state);
  } else if (state.userId !== userId) {
    state.userId = userId;
    state.generation++;
    state.pending.clear();
  }
  return state;
};
```

- **攻坚方案**：建立单会话独立执行的 Promise 串行任务队列；结合 `hotMinIdx` 划分冷热边界，普通热区消息只更新内存，仅在必要时增量写入冷区，兼顾性能与安全。
