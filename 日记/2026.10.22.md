## 🔥 核心难点、关键代码与攻坚复盘

### 1. Windows 系统后台进程拉起 IDE 的前台焦点锁定（Foreground Lock）击穿

- **涉及文件**：`D:\yin\dsh-open-in-ide\index.js`
- **难点所在**：Windows 系统的安全机制（Foreground Lock）会严格限制未处于前台的后台服务或脱离关系的子进程随意抢占用户当前焦点的能力。直接调用 `SetForegroundWindow` 经常被系统静默拦截，窗口只能在任务栏橙色闪烁；此外，若目标 IDE 处于最小化状态，常规前台置顶 API 均无法令其展开。
- **关键代码**：

```csharp
[DllImport("user32.dll")]
public static extern bool ShowWindow(IntPtr hWnd, int nCmdShow);

[DllImport("user32.dll")]
public static extern bool IsIconic(IntPtr hWnd);

[DllImport("user32.dll")]
public static extern IntPtr GetForegroundWindow();

[DllImport("user32.dll")]
public static extern void keybd_event(byte bVk, byte bScan, uint dwFlags, UIntPtr dwExtraInfo);

[DllImport("user32.dll")]
public static extern bool SwitchToThisWindow(IntPtr hWnd, bool fAltTab);

public static bool Focus(IntPtr hWnd)
{
    // 1. 若处于最小化状态，先强制以 SW_RESTORE (9) 恢复正常窗口
    if (IsIconic(hWnd)) ShowWindow(hWnd, 9);
    SetForegroundWindow(hWnd);
    if (GetForegroundWindow() == hWnd) return true;

    // 2. 发送合成 ALT 键事件 (0x12)，破除 Windows 前台焦点锁限制
    keybd_event(0x12, 0, 0, UIntPtr.Zero);
    keybd_event(0x12, 0, 2, UIntPtr.Zero);
    SetForegroundWindow(hWnd);
    if (GetForegroundWindow() == hWnd) return true;

    // 3. 最终兜底尝试 SwitchToThisWindow
    SwitchToThisWindow(hWnd, true);
    return GetForegroundWindow() == hWnd;
}
```

- **攻坚方案**：在 Node.js 中通过临时 PowerShell 脚本注入内联 C# P/Invoke 类型，首先枚举匹配目标 IDE 的顶层窗口句柄，针对窗口标题加权打分匹配目标文件；如果窗口处于最小化（`IsIconic`），先执行 `ShowWindow(hWnd, 9)` 恢复，随后模拟按下并释放 `VK_MENU` (Alt 键) 绕过系统的焦点抢占锁，最后以 `SetForegroundWindow` 与 `SwitchToThisWindow` 双重兜底，彻底实现百发百中的前台唤醒。

### 2. 媒体消息发送失败时本地临时占位清理与虚拟列表视口坍塌

- **涉及文件**：`D:\yin\gddst-coss-frontend\src\views\im\components\chat\ChatBox.vue`、`D:\yin\gddst-coss-frontend\src\store\im\chatStore.ts`
- **难点所在**：前端为了极致的交互反馈，在用户选择大图片或文件时立即生成了 `selfSend=true` 但尚无服务端真实 ID 的本地临时占位对象。当遇到 413 文件过大或网络直接断开时，占位必须被彻底清除，否则下次重启登录仍会作为坏数据出现在消息列表中；然而，若直接从数组中 `splice` 删除该消息，聊天虚拟滚动视口的起始计算指针 `showMinIdx` 会超过当前消息数组的有效索引，直接导致整个聊天框呈现一片空白。
- **关键代码**：

```typescript
// D:\yin\gddst-coss-frontend\src\store\im\chatStore.ts
removeFailedMediaMessage(msgInfo: ChatMessage, chatInfo: ChatInfo): boolean {
  const chat = this.findChat(chatInfo)
  const message = this.findMessage(chat, msgInfo)
  // 必须验证确为本地无正式 ID 的占位消息，避免网络晚到的失败回调误删已成功的正常消息
  if (!message || !isLocalMediaMessage(message)) {
    return false
  }
  this.deleteMessage(message, chatInfo)
  return true
}

// D:\yin\gddst-coss-frontend\src\views\im\components\chat\ChatBox.vue
watch(
  () => props.chat?.messages?.slice() || [],
  (messages, previousMessages) => {
    if (messages.length < previousMessages.length) {
      // 批量移除失败占位后智能回收显示窗口起点，防止由于数组缩短导致起始索引越界穿透
      const current = new Set(messages)
      const removedBefore = previousMessages
        .slice(0, showMinIdx.value)
        .filter(message => !current.has(message)).length
      showMinIdx.value = Math.min(
        Math.max(0, showMinIdx.value - removedBefore),
        Math.max(0, messages.length - 30)
      )
    }
    // ...
  }
)
```

- **攻坚方案**：在 Store 层封装严格带判定守卫的 `removeFailedMediaMessage`，仅对缺少服务端 ID 的本地图片/文件消息生效；在组件层重构 `ChatBox` 的 watch 监听逻辑，计算从当前视口上方被删除的消息条数并动态回缩 `showMinIdx`，保证在任何极端上传失败或网络中断情况下，列表渲染永远平滑稳定。

### 3. VS Code 打开独立文件时的工程上下文孤立与多级追溯

- **涉及文件**：`D:\yin\dsh-open-in-ide\index.js`
- **难点所在**：VS Code CLI 在传入单一文件路径（如 `code -g /path/to/file:10:5`）时，若该文件所属的工作区当前未被任何窗口打开，VS Code 会随意将其放置在“最近活跃”的一个无关窗口内，导致文件失去了项目根目录的配置、语法高亮和模块依赖解析环境。
- **关键代码**：

```javascript
/** 从目标文件路径自下而上递归追溯最近的项目根路径 */
function findProjectFolder(startPath, projectMarkers) {
  let current = statSync(startPath, { throwIfNoEntry: false })?.isDirectory()
    ? startPath
    : dirname(startPath);
  while (true) {
    // 优先匹配版本控制元数据目录
    if (existsSync(join(current, ".git")) || existsSync(join(current, ".hg"))) {
      return current;
    }
    // 次级匹配常见生态工程清单文件
    for (const marker of projectMarkers) {
      if (existsSync(join(current, marker))) {
        return current;
      }
    }
    const parent = dirname(current);
    if (parent === current) {
      return undefined;
    }
    current = parent;
  }
}
```

- **攻坚方案**：在执行拉起指令前，从目标路径开始循环向上递归遍历目录层级，优先匹配 `.git` / `.hg`，其次匹配 `package.json`、`Cargo.toml`、`pom.xml`、`go.mod`、`pyproject.toml` 等工程根标识。寻找到工程目录后，将工程根目录作为文件夹参数与 `--goto` 单文件定位参数一并传递给 VS Code，从而保证每次跳转都能精准复用或启动专属的工程工作区窗口。
