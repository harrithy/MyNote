# WebRTC

## WebRTC是什么

WebRTC(Web Real-Time Communication)，即网页实时通信，是一个开源项目和技术标准。它的核心作用是：允许网页浏览器和移动端设备之间直接建立点对点（P2P）连接，从而实现音频、视频和任意数据的实时传输，且完全不需要安装任何第三方插件。

### P2P连接是什么

P2P(Peer-to-Peer，点对点或对等网络)连接是一种去中心化的网络通信架构。在这种网络模式中，每个参与连接的计算机（称为节点或者对等端）地位都是完全平等的。每个节点既可以作为客户端去请求资源，同时也可以作为服务器向其他节点提供资源。

**P2P核心特征**：

- **去中心化**：网络中没有处于绝对控制地位的中心服务器。数据的传输和网络的维护由所有参与的节点共同完成。
- **资源共享**：每个节点既是资源的提供者也是消费者。
- **动态拓扑**：节点可以随时加入或离开网络，网络结构动态变化。
- **可扩展性**：理论上可以支持大量节点，网络规模不受中心服务器限制。
- **越用越快（高可扩展性）**： 在传统网络中，下载同一个文件的人越多，速度越慢；而在 P2P 网络（如 BT 下载）中，下载的人同时也在上传自己已下载的部分，所以参与者越多，整体的带宽和速度反而越高。
- **抗打击能力强（高容错性）**： 因为没有中心服务器，所以不存在“单点故障”。即使网络中有大量节点突然断线，只要还有节点拥有完整数据，整个网络依然可以正常运转。

常见的 P2P 应用包括：BT 下载、Skype（早期版本）、WebRTC 、区块链网络等。

## WebRTC的核心概念

1. **核心API(The Core APIs)**
   WebRTC 为开发者提供了三个基础的 JavaScript API，用于在浏览器侧控制媒体和连接：
   - **getUserMedia**：用于向用户申请权限并访问本地的硬件设备（摄像头、麦克风或屏幕共享 getDisplayMedia），从而捕获音视频媒体流。
   - **RTCPeerConnection**：WebRTC 的心脏。它负责处理对等连接的整个生命周期，包括网络链路维护、音视频数据的编码/解码、丢包重传、带宽评估以及端到端加密。
   - **RTCDataChannel**：允许在两个对等端之间直接进行低延迟、双向的任意数据传输（如文本、文件或游戏状态），它不仅限于音视频通信。

2. **信令机制(Signaling)**
   在两个浏览器（Peer A 和 Peer B）能够建立 P2P 连接之前，它们必须先在浩瀚的互联网中“发现”彼此，并就如何通信达成一致。WebRTC 标准本身有意没有规定信令的实现方式。
   - 开发者必须自己搭建一个信令服务器（通常使用 WebSocket、Node.js 等技术）。
   - 信令服务器的作用相当于“红娘”，帮助双方交换初始的控制信息，包括各自支持的媒体格式（SDP）以及各自的网络地址（ICE 候选者）。一旦连接建立，信令服务器就不再参与实际的音视频数据传输。
  
3. **会话描述协议 (SDP)**
   SDP (Session Description Protocol) 是在信令阶段交换的核心信息格式。
    - 它是一份纯文本的“配置清单”，详细描述了设备的媒体能力，例如支持哪种视频编解码器（VP8, H.264）、音频采样率、分辨率以及加密密钥参数等。
    - 通信双方通过交换 Offer（提议） 和 Answer（应答） 形式的 SDP，来协商出一个双方设备都能支持的通信标准。

4. **NAT 穿透与 ICE 框架 (NAT Traversal)**
   这是 WebRTC 中最复杂的网络挑战。绝大多数用户的电脑或手机并不拥有直接暴露在公网上的 IP 地址，而是隐藏在路由器的 NAT（网络地址转换）或企业防火墙之后。
    - **ICE (Interactive Connectivity Establishment):** 一个用于寻找和建立最佳网络路径的框架。它会收集本地网络、公网映射和中继等所有可能的连接地址（称为 ICE Candidates），并逐一测试连通性。
    - **STUN (Session Traversal Utilities for NAT):** 一种轻量级的公共服务器。设备向 STUN 发送请求，STUN 会告诉设备它在公网上的“真实 IP 和端口”。拿到这个地址后，双方即可尝试建立直接的 P2P 连接（STUN 在很多常见网络环境下都可以帮助双方尝试建立直接的 P2P 连接，且本身不承载媒体数据，成本较低。）。
    - **TURN (Traversal Using Relays around NAT):** 当双方的网络环境极其严苛（如对称型 NAT）导致 STUN 失败、无法建立直连时，TURN 服务器将作为中继站介入。所有的音视频数据都会通过 TURN 服务器进行转发。TURN 是提升连通率的兜底方案，但实际是否能建立连接仍取决于网络策略、防火墙、UDP/TCP 可用性以及 TURN 服务配置。

5. **强制加密与安全 (Security)**
   WebRTC 将隐私和安全作为架构的基石，不允许任何妥协：
    - 强制 HTTPS: WebRTC 的核心功能（如访问摄像头或建立对等连接）只能在安全上下文（HTTPS 或 localhost）中运行。
    - DTLS 和 SRTP: 音视频流强制使用 SRTP (Secure Real-time Transport Protocol) 进行加密传输，而数据通道和加密密钥的协商则通过 DTLS (Datagram Transport Layer Security) 进行保护。哪怕数据包在公网上被截获，也无法被解密或篡改。

核心流程简述：
通信建立的步骤通常是：本地捕获媒体流 -> 通过信令服务器向对方发送 SDP Offer -> 借助 STUN/TURN 收集并交换 ICE 网络地址 -> 双方找到可用路径，RTCPeerConnection 建立直连 -> 开始 P2P 加密传输流和数据。

### 信令

在 WebRTC 中，信令（Signaling）是建立真正的端到端（P2P）连接之前的“牵线搭桥”过程。
由于 WebRTC 标准本身并没有规定两台设备在茫茫互联网中如何找到彼此，也没有规定它们应该用什么协议（比如 WebSocket、HTTP、SIP 等）来交换初始信息，因此开发者必须自己实现一个信令机制（通常是一个信令服务器）。
可以把信令服务器理解为“相亲介绍所”。在男女双方（Peer A 和 Peer B）正式见面（建立 P2P 直连）之前，他们需要通过红娘（信令服务器）来交换彼此的基本信息。

信令过程中主要交换两类信息：

1. **媒体能力协商 (SDP - Session Description Protocol)**
   - **Offer（提议）**: 发起方（Peer A）生成一份自己的“简历”，说明自己有摄像头、麦克风，支持 H.264 视频编码等，通过信令服务器发给接收方（Peer B）。
   - **Answer（应答）**: 接收方（Peer B）收到后，根据自己的硬件条件生成一份对应的“简历”，同意使用某种双方都支持的音视频格式，然后通过信令服务器回传给 Peer A。
2. **网络地址交换 (ICE Candidates)**
   - 除了媒体格式，双方还需要知道对方的 IP 地址和端口号。
   - 由于 NAT（网络地址转换）和防火墙的存在，设备通常需要借助 STUN/TURN 服务器来获取自己在外网的可用地址（ICE 候选者）。
   - 双方获取到自己的网络地址后，也会通过信令服务器将这些地址打包发送给对方。

核心特征：一旦双方通过信令服务器完成了上述两类信息的交换，底层的 RTCPeerConnection 就会尝试建立直接的 P2P 物理连接。连接成功后，所有的音视频数据直接在两端之间传输，不再经过信令服务器。信令服务器就“功成身退”了。

#### SDP

作为要在信令交换中传递的核心信息载体，SDP（Session Description Protocol）是一种纯文本格式的协议，用于描述多媒体会话的参数和能力。
SDP里到底写了什么？

1. **媒体类型 (Media Types)：** 我要发的是音频、视频，还是纯数据（DataChannel）？
2. **编解码器 (Codecs)：** 支持哪些视频和音频编解码器？比如 VP8、H.264 视频编码，Opus、G.711 音频编码等。
3. **网络信息 (Connection Info)：** 我的基础 IP 地址和端口是什么？（虽然更详细的网络路径由 ICE 负责，但 SDP 会提供一个默认选项）。
4. **安全参数 (Security)：** 用于音视频流强制加密的 DTLS 指纹凭证。

下面为一个极其简化的 SDP 核心片段：

``` Plaintext
v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
s=-
t=0 0
a=fingerprint:sha-256 49:66:12:17:F6:... (加密指纹)
m=video 9 UDP/TLS/RTP/SAVPF 96 97     (核心：声明这是一个视频流)
c=IN IP4 0.0.0.0
a=rtcp:9 IN IP4 0.0.0.0
a=rtpmap:96 VP8/90000                 (声明支持 VP8 编码)
a=rtpmap:97 H264/90000                (声明支持 H.264 编码)
```

**关键行解读：**

- v=(Version):协议版本，永远为0
- o=(Origin):源，包含一个唯一 ID，用于重新协商
- s=(Session Name):会话名称，通常为 "-"
- t=(Timing):会话持续时间，通常为 "0 0" 表示无限期
- a=(Attribute):属性，一个自由文本字段，这是 WebRTC 中最常见的行。比如 a=rtpmap:96 VP8/90000 明确告诉对方：“我支持 VP8 视频格式，时钟频率是 90000”。
  - fingerprint: DTLS 加密指纹，确保媒体流的安全性。
  - rtpmap: 声明支持的编解码器及其参数。
- **m=(Media)**:这是最重要的行。m=video 表示接下来的配置是针对视频流的。
- c=(Connection):连接信息，通常包含 IP 地址。

**它是如何工作的？(Offer / Answer 模型)：**

WebRTC 严格遵循“提议 / 应答 (Offer / Answer)”机制来交换 SDP：

1. 发起方 (Alice) 生成 Offer：Alice 的浏览器扫描自己的麦克风和摄像头，生成一份包含自己所有能力的 SDP 文本（比如：我支持视频 H.264 和 VP8）。她把这段文本通过信令服务器发给 Bob。
2. 接收方 (Bob) 生成 Answer：Bob 收到 Offer 后，根据自己的硬件条件生成一份对应的 SDP 文本，同意使用某种双方都支持的音视频格式，然后通过信令服务器回传给 Alice。
3. 达成共识：Bob 把 Answer 发回给 Alice。至此，双方都明确了接下来的视频流将采用 VP8 格式进行编码和解码。

**WebRTC 中的每个媒体描述都包含一个 direction 属性。direction 属性有四个有效值：**

1. **sendrecv（发送并接收）**
   - 含义：“我既会向你发送媒体流，也准备好接收你发给我的媒体流。”
   - 默认状态：如果你在代码里不进行任何特殊设置，WebRTC 添加音视频轨道时，默认就是双向的 sendrecv。
   - 典型场景：常规的视频会议（如微信视频通话、Zoom 等）。你看着对方，对方也看着你，双方都在同时发送和接收音视频。
2. **sendonly（只能发送）**
   - 含义：“我只会向你发送媒体流，我不接受也不处理你发给我的任何媒体流。”
   - 典型场景：
      - 单向广播/直播：主播的客户端在建立连接时，会声明自己是 sendonly，因为它只需要把画面推出去，不需要看观众的画面。
      - 安防监控摄像头：摄像头只负责把采集到的视频画面发给监控中心，它不需要接收中心的视频。
      - 屏幕共享：当你只共享屏幕而不开麦克风和摄像头时，共享的那个通道就可以配置为 sendonly。
3. **recvonly（只能接收）**
   - 含义：“我是一个纯粹的观众，我只会接收你发来的媒体流，我不会向你发送任何我自己的音视频数据。”
   - 典型场景：
      - 直播观众端：你在看游戏直播时，你的浏览器只需拉取流（接收），不需要把你的脸播出去。
      - 云游戏/云桌面：客户端只负责接收云端渲染好的画面，并只发送控制指令（通过 DataChannel），音视频通道是 recvonly 的。
      - 纯音频会议：如果某个参与者只想听别人说话而不发言，他可以将自己的媒体描述设置为 recvonly。
4. **inactive（未激活/暂停）**
   - 含义：“我们之间的媒体通道暂时保留，但目前既不发送也不接收数据。”
   - 典型场景：
      - 彻底静音 / 挂起通话：当你想暂停某个媒体流，但又不想彻底销毁 RTCPeerConnection（因为重新进行 ICE 穿透很慢）。将其置为 inactive 可以停止带宽消耗，等需要恢复时，再重新协商为 sendrecv 即可实现秒级恢复。
      - 预热连接：有时候为了极速的秒开体验，开发者会在后台提前建立一个 WebRTC 连接，将其设置为 inactive。等用户真正点击“接听”时，再迅速切换状态，省去了漫长的信令交换和打洞时间。

**WebRTC 用到的 SDP 值:**

- **group:BUNDLE** BUNDLE 是一种在单个连接上传输多种类型流量的行为。一些 WebRTC 实现对每个媒体流会使用专用的连接。但 BUNDLE 方式应该是首选。
- **fingerprint:sha-256**: 该属性是 peer 用于 DTLS 证书的哈希值。DTLS 握手完成后，你可以将其与实际证书进行比较，以确认你正在与预期的对象进行通信。
- **setup**: 该属性控制了 DTLS Agent 的行为。在 ICE 连接后，该属性将确定 DTLS Agent 是作为客户端还是服务器来运行。
  - setup:active - 作为 DTLS 客户端运行。
  - setup:passive - 作为 DTLS 服务器运行。
  - setup:actpass - 要求另一个 WebRTC Agent 选择。
- **mid**: 该属性是每个 Media Description 的唯一 ID。用于标识媒体。
- **ice-ufrag**: 该属性是 ICE Agent 的用户片段值。用于 ICE 流量的身份验证。
- **ice-pwd**: 该属性是 ICE Agent 的密码。用于 ICE 流量的身份验证。
- **rtpmap**: 该属性用于将特定的编解码器映射到 RTP 有效负载类型。有效负载类型不是静态的，因此对于每次呼叫，发起者都需要确定每个编解码器的有效负载类型。
- **fmtp**: 该属性为一种有效负载类型定义附加的值。要传递特定的视频配置文件或编码器设置时，这很有用。
- **candidate**: 该属性是来自 ICE Agent 的 ICE 候选地址。这是一个可能被 WebRTC Agent 使用的地址。
- **ssrc**: 一个同步源（SSRC）定义了一个单独的媒体流。label 是此媒体流的 ID。mslabel 是容器的 ID，该容器中可以有多个流。

#### ICE

ICE（Interactive Connectivity Establishment，交互式连接建立）是一个用于在两个对等端（Peer）之间寻找、测试并建立最佳网络连接路径的框架协议。

简单来说，WebRTC 的目标是让两台设备直接进行 P2P（点对点）通信，但现实中的网络环境非常复杂，设备通常隐藏在路由器（NAT）和防火墙背后，没有直接暴露在公网上的 IP 地址。ICE 的工作就是充当一个“寻路者”，想方设法穿透这些障碍，把两台设备连接起来。

为了完成这个任务，ICE 依赖于几个核心组件和概念：

1. **ICE Candidates（候选者）**：ICE 会收集所有可能的网络地址（IP 和端口组合），这些地址被称为 ICE Candidates。它们分为三类：
   - **Host Candidates**：设备本地的 IP 地址和端口，直接从操作系统获取。
   - **Server Reflexive Candidates**：通过 STUN 服务器获取到的、路由器映射在公网上的 IP 和端口。
   - **Relayed Candidates**：通过 TURN 服务器中继的地址，这是在无法建立直接连接时的最后防线。
2. **STUN（Session Traversal Utilities for NAT）**：一个轻量级的公共服务器，STUN 服务器部署在公网上。设备向 STUN 服务器发送一个请求，STUN 服务器会回复：“从我的角度看，你的公网 IP 和端口是 X.X.X.X:Y”。
   - 作用： 帮助隐藏在 NAT 背后的设备发现自己的公网“身份”（即进行 NAT 打洞）。
   - 特点： 极轻量，只负责询问地址，不负责传输实际的音视频数据。
3. **TURN（Traversal Using Relays around NAT）**：当双方的网络环境非常严格（例如遇到了对称型 NAT 或企业级防火墙），STUN 的“打洞”策略会失败。这时就需要 TURN 服务器。
   - 作用： 作为一个公网上的中转站。A 把数据发给 TURN，TURN 再把数据转发给 B。
   - 特点： 消耗带宽和服务器资源较多，因此 ICE 只有在穷尽了所有直连尝试都失败后，才会使用 TURN。

##### NAT 与 NAT 打洞

NAT (Network Address Translation) 翻译过来叫“网络地址转换”。它通常运行在你的路由器上。

**什么是 NAT 打洞 (NAT Hole Punching)？**

在 WebRTC 这样的 P2P 通信中，我们要让 A 和 B 两台设备直接连接。
但是，A 和 B 都藏在各自的 NAT 路由器后面（都在各自公司的分机上）。

- A 直接找 B：A 发消息给 B 的路由器，B 的路由器觉得是骚扰，丢弃。
- B 直接找 A：B 发消息给 A 的路由器，A 的路由器觉得是骚扰，丢弃。这就是所谓的“死锁”。

NAT 打洞，就是巧妙利用路由器的规则，在路由器的“防火墙”上挖出一个允许对方通过的“洞”。 它的核心步骤如下（以 UDP 打洞为例，这也是 WebRTC 中 ICE 和 STUN 服务器做的事情）：

1. 找个“中间人”认门（STUN）：
   - A 和 B 都先向一个公共的 STUN 服务器发送请求，告诉它们的 NAT 路由器：“嘿，我想和对方通信，请帮我看看我的公网 IP 和端口是什么？”
   - STUN 服务器回复 A 和 B 各自的公网地址（比如 A 的公网地址是 203.0.113.1:54321，B 的公网地址是 203.0.113.2:54322）。
2. 交换名片（信令）：
   - A 和 B 通过信令服务器交换彼此的公网地址（ICE Candidates）。
   - A 知道了 B 的公网地址，B 也知道了 A 的公网地址。
3. 同时敲门（打洞）：
   - A 向 B 的公网地址（203.0.113.2:54322）发送数据，B 向 A 的公网地址（203.0.113.1:54321）发送数据，从而在各自的 NAT 路由器上打开一个临时的通信通道。
   - 如果双方的 NAT 都是“对称型 NAT”，或者其中一方在企业防火墙后面，这个打洞过程可能会失败。这时就需要 TURN 服务器来中转数据。
   - 成功打洞后，A 和 B 就可以直接通过这个“洞”进行 P2P 通信了，数据不再经过 STUN 服务器。
